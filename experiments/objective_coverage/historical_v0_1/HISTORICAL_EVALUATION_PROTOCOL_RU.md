# OBJECTIVE_COVERAGE_HISTORICAL_EVALUATION v0.1

Статус: `PROTOCOL_FROZEN / DATASET_NOT_SELECTED / NOT_RUN / NOT_VALIDATED`

## Назначение

Следующий этап после синтетического bakeoff. Его задача — проверить три уже существующих семейства формул Objective/Coverage на исторических временных данных без подглядывания в будущее.

Этот документ замораживает правила ДО выбора конкретного исторического кейса и ДО получения результата.

## Замороженные кандидаты

Источник формул: `experiments/objective_coverage/v0_1/objective_coverage_bakeoff.py`.

- `A_LINEAR_COVERAGE`
- `B_GEOMETRIC`
- `C_HYBRID_MIN_CAP`

На этом этапе запрещено менять формулы, веса или provisional cap после просмотра будущей части исторического кейса.

## Главный принцип

```text
INFORMATION_AVAILABLE_AT_T <= INPUT_AT_T
FUTURE_INFORMATION > T == FORBIDDEN
HISTORICAL_FIT != FORECAST_VALIDATION
SYNTHETIC_WINNER != HISTORICAL_WINNER
CONFIDENCE_IN_ANALYSIS != EVENT_PROBABILITY
```

## Единица испытания

Один исторический кейс должен содержать:

1. `case_id` — стабильный идентификатор;
2. `cutoff_time` — момент, в котором Футуролог условно останавливается;
3. `observation_window_start` — начало доступного прошлого;
4. evidence (свидетельства), реально опубликованные не позднее cutoff;
5. заранее определённый future outcome window (окно будущего результата);
6. outcome label, определяемый только после фиксации входа;
7. provenance (происхождение) каждого входного элемента.

## Анти-leakage правила

- Использовать дату первоначальной публикации, а не дату позднейшего пересказа.
- Позднейшие исправления, ретроспективные обзоры и статьи «что мы теперь знаем» не входят во вход до cutoff.
- Нельзя вычислять feature (признак) из данных, которые появились после cutoff.
- Нельзя выбирать только известные успешные кризисы/события. Нужны также отрицательные и спокойные интервалы.
- Нельзя менять outcome definition после просмотра score.
- Если дата или provenance сомнительны, элемент получает `REVIEW_REQUIRED` и не считается надёжным входом.

## Входной контракт

Для каждого snapshot (среза):

```text
measured_score        [0,1]
evidence_coverage     [0,1]
source_independence   [0,1]
freshness             [0,1]
pipeline_completeness [0,1]
observed_noise        [0,1]
```

Все три формулы получают абсолютно один и тот же EvidenceState.

## Выход

Для каждой формулы сохраняются:

- raw effective confidence;
- timestamp;
- case_id;
- cutoff_time;
- outcome label;
- lead time до outcome, если outcome наступил;
- missing/degraded flags;
- полный audit trail (журнал происхождения расчёта).

## Метрики

### 1. Discrimination (различение)
Проверяем, ставит ли формула реальные положительные случаи выше отрицательных. Основная метрика: ROC-AUC, дополнительная PR-AUC при дисбалансе классов.

### 2. Calibration (калибровка)
Только как диагностическая проверка. Поскольку текущий effective confidence НЕ объявлен вероятностью события, Brier score и reliability curve не превращают его автоматически в probability. Они показывают, насколько числовая шкала согласуется с частотой исходов.

### 3. Early-warning usefulness (полезность раннего предупреждения)
Для заранее зафиксированных operational thresholds (рабочих порогов) измеряем:

- долю положительных кейсов, замеченных до события;
- median lead time;
- false alarms на единицу времени;
- долю времени в состоянии alert.

### 4. Coverage honesty (честность покрытия)
Отдельно проверяем, не выдаёт ли формула высокую confidence при низком coverage, independence или pipeline completeness.

## Пороговая дисциплина

Первый исторический прогон выполняется без подгонки порогов под test set.

Если для operational metrics нужны пороги, они должны быть либо:

- заранее зафиксированы до просмотра test outcome;
- либо подобраны только на отдельном calibration/training interval и затем заморожены.

## Минимальная схема разбиения

Предпочтительно:

```text
PAST / CALIBRATION WINDOW -> FROZEN PARAMETERS -> LATER / TEST WINDOW
```

Для нескольких кейсов допускается rolling-origin evaluation (пошаговая историческая проверка), но каждый шаг обязан соблюдать временную причинность.

## Negative controls

Обязательны:

- спокойные интервалы без целевого события;
- периоды с громким информационным шумом, который не привёл к outcome;
- множественные сообщения, восходящие к одному источнику;
- неполный pipeline;
- поздно появившаяся информация, специально исключённая до cutoff.

## Критерий прохождения этапа

Ни одна формула не объявляется победителем только по одной метрике или одному событию.

Решение принимается по совокупности:

```text
DISCRIMINATION
+ EARLY_WARNING_USEFULNESS
+ COVERAGE_HONESTY
+ ROBUSTNESS_ACROSS_CASES
+ AUDITABILITY
```

Если данных недостаточно, правильный результат этапа: `INSUFFICIENT_EVIDENCE`, а не выбор победителя.

## Первый прикладной корпус

Конкретная сфера здесь намеренно НЕ зафиксирована. Мы сначала замораживаем метод проверки. Геополитика / OSINT / экономика подключаются следующим отдельным dataset-specification документом, чтобы предметная область не изменила правила экзамена задним числом.
