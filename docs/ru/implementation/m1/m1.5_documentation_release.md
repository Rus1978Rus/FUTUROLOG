# Entropy-RG v3.0-domain-neutral

## 1. Что такое Entropy-RG v3.0-domain-neutral

Entropy-RG v3.0-domain-neutral — это алгоритмическое scoring-ядро для анализа аномальных actor/event-сигналов в доменно-нейтральных потоках данных. Пакет принимает нормализованные `actors`, `events`, `topics`, исторический контекст, графовый контекст и baseline-признаки, после чего возвращает component scores, `universal_risk`, `trust_adjustment`, `final_score`, reasons и metadata. Версия v3.0 завершает Milestone M1: доменная модель отвязана от маркетплейса, scoring-ключи приведены к canonical naming, API возвращает dual output, а состояние калибровки явно отображается в каждом response.

## 2. Связь с проектом «Футуролог» и ERG-CAD

Entropy-RG является scoring-core проекта «Футуролог». Инфраструктурный слой ENRA отвечает за приём сигналов, очереди, priority lanes, audit path и compensation events. Entropy-RG отвечает за математическую оценку структуры сигнала. Теоретическая база проекта — авторский препринт ERG-CAD, где риск рассматривается как устойчивость информационной асимметрии через действия, последовательности, графы и масштабы. В v3.0 реализована только universal-интенсивность сигнала; objective layer из ERG-CAD зафиксирован в API как будущий слой, но ещё не реализован.

## 7. Конфигурация: alpha, gamma, веса, версии

Metadata v3.0:

```text

alpha = 0.3
gamma = 0.07

```

Universal layer weights в v3.0:

| Внутренний/публичный ключ | Вес |
|---|---:|
| `gibbs` | 0.25 |
| `rg_persistence_score` | 0.22 |
| `sequential_anomaly_score` | 0.18 |
| `surprise` | 0.18 |
| `graph_risk` | 0.12 |
| `trust_penalty` | 0.10 |

`gibbs` и `surprise` — implementation building blocks. Они присутствуют в response, потому что текущий universal_risk использует их, но они не являются canonical компонентами ERG-CAD верхнего уровня.

Trust adjustment:

```text
weighted_base = sum(weights × component_scores) - gamma × trust_adjustment
gamma = 0.07
```

## 8. Calibration status

`calibration_status = "uncalibrated"` означает, что стартовые веса и `gamma` не являются результатом backtest или доменной оптимизации. Они зафиксированы как стартовая конфигурация на основе препринта и архитектурных решений M1.

Важно:

```text
final_score в v3.0 — это сырой сигнал интенсивности, не вероятность события.
```

Его нельзя интерпретировать как:

- вероятность наступления события;
- финансовый прогноз;
- окончательный аналитический вывод;
- юридически значимое решение;
- медицинский или safety-critical вывод.

Корректная интерпретация:

```text
final_score = ранний сигнал для сортировки, маршрутизации и последующего аудита.
```

# Entropy-RG v3.0-domain-neutral Technical Specification

## 1. Назначение и границы пакета

Entropy-RG v3.0-domain-neutral — это scoring-core для доменно-нейтрального анализа actor/event-сигналов. Он не является orchestration-системой, не управляет очередями и не реализует полный audit workflow. Эти функции относятся к ENRA в проекте «Футуролог».

Пакет отвечает за:

- расчёт universal scoring;
- сбор component scores;
- confluence bonus;
- trust adjustment;
- dual output;
- metadata;
- compatibility aliases;
- базовые explanations;
- подготовку output для дальнейшей маршрутизации.

Пакет не отвечает за:

- полноценный Objective Layer;
- приоритетные очереди Q0/Q1/Q2/Q3;
- Hash-chain MVP;
- human review loop;
- калибровку весов;
- адаптеры внешних источников;
- принятие окончательных решений.

## 2. Domain-neutral модель

## 4. Universal layer components

v3.0 реализует universal layer как интенсивность сигнала. Objective Layer не реализован.

| Компонент / ключ | Вес | Статус | Описание |
|---|---:|---|---|
| `gibbs` | 0.25 | building block | Внутренний статистический примитив локального/contextual deviation |
| `rg_persistence_score` | 0.22 | implemented/partial | Устойчивость информационного остатка при укрупнении масштаба |
| `sequential_anomaly_score` | 0.18 | implemented/partial | Последовательная аномальность через trajectory/history |
| `surprise` | 0.18 | building block | Large deviation primitive относительно baseline |
| `graph_risk` | 0.12 | implemented/partial | Риск, связанный с графовой структурой |
| `trust_penalty` | 0.10 | implemented | Штраф за низкое доверие / высокий trust penalty |

`gibbs` и `surprise` присутствуют в v3.0 response, потому что текущая реализация использует их для расчёта universal_risk. В архитектурной модели ERG-CAD они не являются самостоятельными canonical компонентами верхнего уровня. Они остаются implementation building blocks до разделения `local_action_risk` и `profile_deviation` в M2.

## 5. Trust adjustment

Trust adjustment — отдельный modifier, не входящий в `DEFAULT_WEIGHTS`.

Формула применения:

```text
weighted_base = sum(weights × component_scores) - gamma × trust_adjustment
gamma = 0.07
```

Семантика:

- `trust_adjustment` хранится как положительная величина;
- применяется со знаком минус;
- в legacy block отображается как `robustness`;
- не должен отрицаться или масштабироваться внутри `legacy_component_scores`.

## 6. Финальная формула в M1

В M1.4/M1.5 финальный score:

```text
final_score = universal_risk
universal_risk = weighted_base + confluence_bonus
weighted_base = sum(weights × component_scores) - gamma × trust_adjustment
```

Objective Layer не участвует в расчёте.

```text
objective_risk = null
objective_component_scores = {}
objective_layer_active = false
```

`alpha = 0.3` присутствует только как metadata.

```text
alpha_active = false
```

## 7. Каноническая формула, планируемая на M3+

Целевая формула после реализации Objective Layer:

```text
final_score =
    universal_risk × (alpha + (1 - alpha) × objective_risk)
    - gamma × trust_adjustment
```

Эта формула не применяется в v3.0. Она зафиксирована как roadmap-level design.

## 8. Двухслойная модель ERG-CAD

ERG-CAD разделяет риск на два слоя:

| Слой | Смысл | Статус в v3.0 |
|---|---|---|
| Universal Risk Score | Интенсивность риска | Частично реализован |
| Objective Risk Score | Устойчивость и проверяемость риска | Не реализован |

Objective Layer будет состоять из:

- `scale_stability`;
- `temporal_persistence`;
- `source_redundancy`;
- `observer_agreement`;
- `noise_separation`.

В v3.0 эти компоненты не рассчитываются.

## 13. Sealing и audit

M1 не реализует Hash-chain MVP. Если scoring output подписывается через HMAC, metadata-поля v3.0 могут входить в payload подписи. Это означает, что HMAC snapshots изменятся при переходе с v2.2/M1.3 на M1.4. Это ожидаемое изменение схемы payload, не изменение HMAC-алгоритма.

Hash-chain MVP отнесён к M6.

## 14. Расширение

### Как добавить `flow_asymmetry` в M2

M2 должен:

- добавить компоненту `flow_asymmetry`;
- вернуть веса universal layer к препринтной конфигурации;
- обновить response schema;
- обновить tests;
- обновить baseline JSONL.

Не добавлять `flow_asymmetry` в M1.

### Как добавить Objective Components в M3

M3 должен:

- реализовать `temporal_persistence`;
- затем `observer_agreement`;
- затем `source_redundancy`;
- затем `noise_separation`;
- затем `scale_stability`;
- переключить `objective_layer_active` на `true` только после минимальной работоспособности слоя;
- активировать alpha-формулу только после отдельного baseline update.

## 12. FAQ

### Почему gamma изменилась с 0.05 на 0.07?

В M1.3 `gamma = 0.05` использовалась только для доказательства числовой эквивалентности старому `robustness`-весу. В M1.4 `gamma = 0.07` становится каноническим стартовым значением из архитектуры v1.1. Это намеренно меняет baseline.

### Почему objective_risk = null?

Потому что Objective Layer не реализован в M1. Значение `null` честно показывает отсутствие расчёта. Использовать 0 или 1 было бы хуже: 0 выглядело бы как активное обнуление, 1 — как заглушка, скрывающая отсутствие слоя.

### Почему alpha = 0.3 указано, но не применяется?

`alpha = 0.3` — metadata для будущей формулы M3+. В M1 `alpha_active = false`, поэтому alpha не участвует в расчёте.

### Что значит uncalibrated в weights_version/calibration_status?

Это значит, что веса и пороги являются стартовой конфигурацией, а не результатом доменного backtest. `final_score` нельзя считать вероятностью события или откалиброванной мерой риска.

### Можно ли использовать deprecated endpoints после v3.0?

Да, до v3.2. После этого старые endpoints и aliases должны быть удалены или перенесены в отдельный compatibility package.

# docs/HEALTHCHECK_AND_METADATA.md

# Healthcheck and Metadata

## 1. Что возвращает healthcheck

Healthcheck возвращает технический статус пакета и metadata текущей scoring-конфигурации. Он нужен для проверки, что API, security layer, scoring layer и dashboard используют одну и ту же версию модели и одну и ту же конфигурацию.

Healthcheck не доказывает корректность score. Он показывает, что сервис запущен и metadata согласованы.

## 2. Полный пример JSON response

```json
{
  "status": "ok",
  "model_version": "entropy-rg-v3.0-domain-neutral",
  "weights_version": "preprint-v1-uncalibrated",
  "calibration_status": "uncalibrated",
  "alpha": 0.3,
  "gamma": 0.07,
  "dual_output": true,
  "alpha_active": false,
  "objective_layer_active": false
}
```

## 3. Семантика полей

| Поле | Тип | Значение | Семантика |
|---|---|---|---|
| `status` | string | `ok` / `degraded` / `unhealthy` | Техническое состояние сервиса |
| `model_version` | string | `entropy-rg-v3.0-domain-neutral` | Версия scoring model |
| `weights_version` | string | `preprint-v1-uncalibrated` | Версия весов |
| `calibration_status` | string | `uncalibrated` | Статус калибровки |
| `alpha` | float | `0.3` | Будущий параметр Objective Layer formula |
| `gamma` | float | `0.07` | Вес trust adjustment |
| `dual_output` | bool | `true` | API возвращает legacy и canonical blocks |
| `alpha_active` | bool | `false` | Alpha не участвует в расчёте M1 |
| `objective_layer_active` | bool | `false` | Objective Layer не реализован |

## 4. Как интерпретировать calibration_status = "uncalibrated"

`uncalibrated` означает:

- веса взяты из стартовой архитектурной конфигурации;
- параметры не прошли backtest;
- `final_score` не является вероятностью;
- thresholds для production должны быть проверены отдельно;
- score пригоден для сортировки и triage, но не для автоматических критических решений.

Корректная реакция клиента:

```text
Использовать final_score как ранжирующий сигнал и передавать важные случаи в audit/human review.
```

Некорректная реакция:

```text
Интерпретировать final_score = 0.8 как 80% вероятность события.
```

## 5. Когда healthcheck должен возвращать degraded или unhealthy

### degraded

`status = "degraded"` уместен, если:

- API доступен, но часть источников недоступна;
- scoring работает, но baseline устарел;
- dashboard недоступен, но scoring API работает;
- healthcheck обнаружил рассинхронизацию non-critical metadata;
- deprecated compatibility работает не полностью;
- baseline fixture отсутствует в dev-среде.

### unhealthy

`status = "unhealthy"` уместен, если:

- scoring API не может рассчитать score;
- metadata source of truth недоступен;
- `model_version` отличается между модулями;
- HMAC/security layer падает;
- CSV/schema несовместимы с текущим кодом;
- critical tests не проходят;
- response не содержит обязательных M1.4 fields.
