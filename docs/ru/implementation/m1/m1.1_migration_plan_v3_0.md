# migration_plan_v3_0.md

# План миграции Entropy-RG v2.2 → v3.0-domain-neutral

Статус: M1.1, план до написания кода  
Проект: «Футуролог»  
Целевая версия: `entropy-rg-v3.0-domain-neutral`  
Основание: `canonical_scoring_mapping_v1.md`, `futurolog_architecture_v1.1.md`, ERG-CAD  
Ограничение: архив `entropy_rg_anomaly_detector_EN_v2_2_FINAL.zip` не был открыт при подготовке этого плана. Все предположения о фактических файлах архива помечены `[REQUIRES_VERIFICATION]`.

## 1. Сводка миграции

Миграция v3.0-domain-neutral делает первый безопасный код-шаг Entropy-RG: убирает маркетплейсную привязку `seller/listing/category/region`, переводит публичную модель на `actor/event/topic/location`, вводит canonical scoring output и добавляет двойной output для совместимости. v3.0 не реализует новые scoring-компоненты, не добавляет Objective Layer, не меняет формулы, пороги, confluence-логику и HMAC-логику. `flow_asymmetry`, разделение `local_action_risk` и `profile_deviation`, а также полноценная реализация Objective Layer остаются на v3.1+.

## 5. Таблица изменений по файлам

### app/scoring.py

Что меняется:

- Переименовать public scoring keys: `trust` → `trust_penalty`, `residue` → `rg_persistence_score`, `sequential` → `sequential_anomaly_score`, `graph` → `graph_risk`.
- Оставить `gibbs` и `surprise` как legacy building blocks.
- Убрать `robustness` из `DEFAULT_WEIGHTS`.
- Ввести `trust_adjustment` как отдельный modifier.
- Добавить `alpha = 0.3`, `gamma = 0.07`, `weights_version`, `calibration_status`.
- Обновить функцию интеграции score: собрать legacy scores, построить canonical scores, вернуть dual output.
- Обновить доменные поля: `seller_id/listing_id/category_id` → `actor_id/event_id/topic_id`.
- Подключить `app/canonical_mapping.py`.

Что нельзя трогать:

- Формулы локальных вычислений.
- `robust_z_score`, MAD, gaussian tail probability.
- Логику `confluence_bonus`.
- Числовые пороги risk levels.
- Decay, clipping и normalization, если они уже реализованы.

Порядок изменений:

1. Добавить import из `canonical_mapping.py`.
2. Сформировать `legacy_component_scores` без изменения формул.
3. Передать scores в `build_dual_output`.
4. Заменить public return на dual output.
5. После успешных тестов заменить request/domain keys.

Риски:

- `trust` может быть positive trust score.
- Вынос `robustness` может изменить итоговый score.
- Confluence logic может обращаться к старым ключам.

## 12. Риски и меры снижения

### Риск 1: семантическая ошибка при `trust` → `trust_penalty`

Что может пойти не так: old `trust` может быть positive trust score, а не penalty.  
Где: `app/scoring.py`, `app/canonical_mapping.py`, `app/explanations.py`.  
Как обнаружить: создать тесты high-trust и low-trust; проверить направление score.  
Как откатить: вернуть old `trust` в legacy block; в canonical block использовать `trust_penalty = 1 - trust`, только если old trust confirmed positive. Если знак неясен — `[OPEN_QUESTION]`.

### Риск 2: потеря данных при CSV-миграции

Что может пойти не так: unknown columns удалены.  
Где: `data/*.csv`, converter, calibration.  
Как обнаружить: сравнить columns, row count, non-null count.  
Как откатить: restore backup; повторить migration с preservation unknown columns.

### Риск 3: несовместимость dual output с API-клиентами

Что может пойти не так: клиенты ждут `component_scores`.  
Где: `app/api.py`, `app/scoring.py`, dashboard.  
Как обнаружить: API snapshot tests, old client smoke.  
Как откатить: вернуть `component_scores` как deprecated alias to `legacy_component_scores` до v3.2.

### Риск 4: поломка `confluence_bonus`

Что может пойти не так: confluence ищет legacy keys, а получает canonical.  
Где: `app/scoring.py`, `app/confinement.py`, `app/sequential.py`.  
Как обнаружить: unit tests на confluence cases; compare v2.2 vs v3.0 bonus.  
Как откатить: оставить confluence logic на legacy keys внутри internal computation; mapping делать после confluence.

### Риск 5: некорректный final_score из-за `robustness` → `trust_adjustment`

Что может пойти не так: old robustness участвовал иначе, а теперь вычитается через gamma.  
Где: `app/scoring.py`, `app/canonical_mapping.py`.  
Как обнаружить: compare distribution before/after; test low/medium/high robustness.  
Как откатить: сохранить `legacy_final_score`; новый final score считать отдельно; при большом delta включить compatibility mode.

### Риск 6: рассинхронизация SYSTEM_META

Что может пойти не так: healthcheck показывает v3.0, а API/security — v2.2.  
Где: `app/security.py`, `app/scoring.py`, `app/api.py`, `healthcheck.py`.  
Как обнаружить: centralized metadata test; grep old model_version.  
Как откатить: создать единый `get_system_meta()` и импортировать его везде.

### Риск 7: SQLite schema mismatch

Что может пойти не так: код ищет `actor_id`, база содержит `seller_id`.  
Где: `app/state_store.py`, SQLite db, migrations.  
Как обнаружить: schema introspection, sequence update test.  
Как откатить: restore db backup; добавить compatibility read; для MVP пересоздать db, если state не критичен.

### Риск 8: Deprecated endpoints без deprecation header

Что может пойти не так: клиенты не узнают, что endpoint устаревает.  
Где: `app/api.py`.  
Как обнаружить: `curl -i /seller/{id}`.  
Как откатить: добавить helper/middleware для deprecated routes и tests на headers.

### Риск 9: mechanical replace ломает reference examples

Что может пойти не так: `category` заменяется внутри reference-domain текста, где нужно сохранить старый пример.  
Где: README, docs, data examples.  
Как обнаружить: manual diff review.  
Как откатить: откатить mechanical replace commit; делать rename по файлам.

### Риск 10: tests зелёные, но математика изменилась

Что может пойти не так: snapshots обновлены без regression equality.  
Где: tests/CI.  
Как обнаружить: mandatory v2.2 vs v3.0 score comparison.  
Как откатить: вернуть formulas; сохранить old internal keys до equality.

## 15. Примечания для ревью

1. Все места с `[REQUIRES_VERIFICATION]` должны быть проверены после распаковки архива.
2. Все места с `[OPEN_QUESTION]` нельзя решать автоматически в коде.
3. Цель M1 — безопасное переименование и совместимость, а не улучшение модели.
4. Любое изменение формулы должно быть вынесено в отдельный diff и отдельно согласовано.
5. Главный regression criterion: переименование не должно менять математический смысл score.
